# 1.0 implementation plan

Tracking: [GitHub issue #1](https://github.com/bjm1244/pgwarc_lance/issues/1).

Initial supported scope: Linux x86_64, PostgreSQL 16, one node, local Lance storage, trusted operators and a shared corpus.

This plan is a readiness target. It does not claim that the current prototype is production ready.

## Batch execution contract

- The existing batch runs at 01:30, 07:30, 13:30 and 19:30 Asia/Seoul using GPT-6 Luna with reasoning max.
- One serialized cycle selects the earliest eligible issue whose prerequisites have been published successfully. An unfinished issue can span multiple cycles.
- Each issue has stable acceptance criteria C1–C3. Completion requires actual evidence for every criterion and successful publication checks and push.
- Partial progress references the issue without closing it. Failed publication retries the verified snapshot before starting new development.
- A blocked issue records its reason and resume condition. Independent work can proceed; dependent work remains queued.
- Human relevance labels and final release approval cannot be fabricated. Issues awaiting these inputs remain open.
- Long soak tests retain checkpoints and actual elapsed time across cycles. A short model run is not evidence of a long soak.
- The batch never creates an official 1.0 tag, uploads release binaries or deploys to production.
- Machine-readable scope and progress: [plan](v1.0-plan.json), [status](v1.0-status.json). Private logs and evidence paths are not published.

The queue is managed by the existing operator batch. New issues or changed acceptance criteria require an explicit queue update; they do not silently expand the batch scope.

## Acceptance criteria

### #2: 전체 적재 재현성과 +18 posting 차이 규명

- **C1**: 동일 원본·추출·tokenizer 버전을 고정하고 기존 DB와 재적재의 +18 posting/+18 tf 차이를 문서·term 수준으로 설명한다. 원인을 확인하기 전 인덱스 버그로 단정하지 않는다.
- **C2**: 실제 원본을 이용한 최소 재현과 회귀 fixture를 만들고 동일 입력 반복 실행의 문서/posting/tf fingerprint가 일치한다.
- **C3**: raw/imported/metadata-only/failed/policy-skipped 수와 원인, 입력·설정 checksum을 합계 검증 가능한 manifest로 남긴다.

### #3: PG16 공식 패키징·SQL 생성 경로 복구

- **C1**: cargo-pgrx GLIBC 호환 문제를 해결하고 고정 toolchain/lockfile에서 공식 install SQL을 생성한다. 이전 SQL 복사로 대체하지 않는다.
- **C2**: 생성된 artifact로 fresh install, 네 SQL 회귀, 실제 지원 이전 버전에서 populated upgrade를 통과한다.
- **C3**: Linux x86_64·PG16의 clean build/reproduction 명령, checksum, CI 경로와 지원 범위를 문서화한다.

### #4: 바이너리 고지 공백·SBOM·의존성 관리 정리

- **C1**: random_word와 seahash의 package-level primary license text와 출처를 검토하거나 호환 가능한 의존성 교체로 공백을 없앤다. 추측한 일반 라이선스로 대체하지 않는다.
- **C2**: 실제 배포 대상의 Cargo/native/compiler/vendor 고지와 SBOM을 lock/artifact checksum에 묶고 엄격한 notice 수집을 통과한다.
- **C3**: 현재 RustSec 취약점/unsound/yanked를 예외 없이 검사하고 미관리 경고·vendored patch 출처와 제거 조건을 기록한다.

### #5: DB 커밋 이후 색인 반영 계약과 durable outbox

- **C1**: SQL rollback이 Lance 쓰기를 되돌리지 못하는 현재 경계를 개선할 outbox/worker 계약을 구현하고 원자성·eventual consistency 범위를 명시한다.
- **C2**: 커밋된 작업만 반영하고 실행 중단·중복 전달·재시작에도 작업 유실과 잘못된 완료 표시가 없다.
- **C3**: 반영 버전·지연·실패·완료 대기 및 읽기 일관성 계약을 실제 동시성/rollback/종료 시험으로 검증한다.

### #6: PG–Lance 대사·idempotent 갱신·복구

- **C1**: 안정된 document ID/revision으로 중복·누락·오래된 벡터·고아 행을 탐지하는 read-only doctor를 제공한다.
- **C2**: 중복 재시도와 동시 갱신에서도 BM25·metadata·Lance 상태가 정해진 revision으로 수렴한다.
- **C3**: 부분 실패 후 dry-run 대사와 명시적 복구를 실제 DB에서 검증하고 파괴적 작업을 기본으로 실행하지 않는다.

### #7: 증분 적재·checkpoint·재개 가능한 import

- **C1**: archive/record/설정별 checkpoint와 import-run 상태를 남기고 중단 지점부터 재개한다.
- **C2**: 같은 파일 반복, 부분 실패, embedding 실패, worker 종료 후에도 중복 없이 갱신하며 실패 레코드만 재처리할 수 있다.
- **C3**: 실제 WARC 적재에서 record accounting, 메모리/임시 디스크 한도와 재개 후 fingerprint를 검증한다.

### #8: 문서 삭제·tombstone·벡터 정리 lifecycle

- **C1**: 삭제와 재생성에 일관된 document revision/tombstone 계약을 두고 검색 결과에서 삭제 문서를 배제한다.
- **C2**: 실패·재시도·동시 upsert/delete에서 metadata/BM25/vector가 다시 나타나거나 중복되지 않는다.
- **C3**: 이전 dataset version 보존과 compaction/GC·복원 정책을 명시하고 보존된 스냅샷을 임의 삭제하지 않는다.

### #9: 일관된 백업·새 인스턴스 복원·장애 복구

- **C1**: PostgreSQL과 Lance의 일관된 복구 지점 및 역할/설정을 함께 보존하고 새 인스턴스에서 복원한다.
- **C2**: 정상 SIGTERM 종료와 SIGKILL/디스크 부족/손상/중단을 구분해 시험하고 counts/revisions/retrieval/grants를 확인한다.
- **C3**: 소유한 격리 환경에서만 시험하고 복구 절차·허용 데이터 손실·복구 시간의 실측 범위를 남긴다.

### #10: 논리 컬렉션·임베딩 모델/버전 manifest

- **C1**: 컬렉션 ID와 관리된 dataset 경로, 모델/차원/정규화/청크 설정·버전을 manifest로 관리한다.
- **C2**: 차원/모델/청크 버전 혼합을 거부하고 재색인 중 활성 버전 전환·되돌리기 계약을 검증한다.
- **C3**: 신뢰한 운영자·공유 corpus 범위를 유지하고 tenant isolation을 암묵적으로 주장하지 않는다.

### #11: 문서 청크와 원문 출처 추적

- **C1**: 긴 문서를 외부 importer에서 청크화하고 안정된 parent/chunk ID 및 offset/version을 보존한다.
- **C2**: 검색 결과에서 원 URL·수집 시각·문서/청크 위치를 확인하며 확인되지 않은 PDF 페이지 번호를 만들어내지 않는다.
- **C3**: 긴 문서 truncation·중복·문서 갱신·삭제와 실제 임베딩 적용을 재현 가능한 회귀로 검증한다.

### #12: 후보 생성부터 적용하는 조건 검색

- **C1**: 도메인·날짜·언어·형식·컬렉션의 동일 eligibility 조건을 BM25와 vector 후보 생성에 적용한다.
- **C2**: top-k 이후 WHERE로 누락되던 사례, 일치 문서가 k보다 적은 경우와 ANN/정확 검색의 의미를 시험한다.
- **C3**: 필터 입력을 제한/매개변수화하고 SQL injection·권한·resource 한도 회귀를 통과한다.

### #13: candidate_k·RRF 옵션과 검색 설명

- **C1**: 최종 k와 후보 수를 분리하고 안전한 상한·기본값·결정적 tie-break를 제공한다.
- **C2**: BM25/vector 가중치와 RRF 옵션을 명시적으로 제공하고 각 소스의 순위·기여를 설명한다.
- **C3**: 기본 검색 계약의 호환성과 candidate 확장·빈 결과·한 소스 실패·유효하지 않은 옵션을 검증한다.

### #14: 출처가 있는 snippet·안전한 highlight

- **C1**: 작은 SQL/client 표면으로 결과 snippet과 matched span을 반환하고 원 청크/문서로 이동할 수 있다.
- **C2**: HTML/script escaping, Unicode/CJK 경계, 길이 한도, 일치 없음 사례를 시험한다.
- **C3**: 점수 기여/출처와 본문 일부를 사용하는 최소 검색 예제를 제공하고 불필요한 DB 내부 렌더링을 늘리지 않는다.

### #15: 전체 raw-WARC·charset·문서 추출 안전성

- **C1**: 실제 segment 전체를 처음부터 처리하고 HTML/text/PDF text/DOCX 지원 및 비지원/OCR 필요 문서를 정확히 집계한다.
- **C2**: 잘못된 charset·oversized token·압축/추출 한도와 실패 문서 보존/재시도를 검증하고 replacement 문자의 의미 정확성을 과장하지 않는다.
- **C3**: raw/imported/metadata-only/failed/skipped를 전부 대사하고 원문·SQL·vector·자격증명을 공개 소스에 넣지 않는다.

### #16: 운영 corpus의 독립 relevance 평가

- **C1**: 권리와 출처를 확인한 운영형 corpus 및 실제 embeddings에 사람이 독립 판정한 relevance labels를 준비한다. 모델 생성 답이나 self-hit을 인간 gold로 부르지 않는다.
- **C2**: 질의·라벨·모델 checksum 및 tuning/holdout 분리를 고정하고 BM25/vector/hybrid Recall@k·MRR·nDCG를 비교한다.
- **C3**: 합격 기준은 최종 결과를 보기 전에 정하고 사전 기준/회귀 허용 범위를 통과한다. 사람이 확인한 labels가 없으면 blocker로 남긴다.

### #17: 규모별 검색·적재 SLA와 인덱스 비용 결정

- **C1**: 문서/청크 규모·길이·차원·서버·query mix·동시성을 고정하고 합격 예산을 먼저 정의한다.
- **C2**: 현행 corpus에서 10만→100만 규모를 단계적으로 검증하되 검증 전 지원 규모로 광고하지 않는다. p95/p99, ingest, CPU/RSS/temp/WAL/disk를 측정한다.
- **C3**: frequency index의 읽기 이득과 CPU/WAL/공간 비용을 같은 workload로 평가해 유지/옵션화/제거를 결정한다. host 부하 차이를 성능 향상으로 단정하지 않는다.

### #18: 장시간 혼합 부하·자원 한도·취소 검증

- **C1**: 정의한 예산으로 24–72시간 혼합 읽기/쓰기 시험을 실제 경과 시간과 함께 수행한다. 여러 회차에 걸친 실험은 소유한 job/checkpoint로 이어간다.
- **C2**: OOM·누수·temp/WAL/disk 증가·지연·취소 후 backend 재사용과 정상 종료를 점검한다.
- **C3**: 장애/장시간 시험의 결과와 한계를 보존하고 80분 회차 완료를 장시간 운영 승인으로 대체하지 않는다.

### #19: 색인 상태·지연·실패 metrics와 운영 doctor

- **C1**: 반영 지연·queue depth·실패·활성 버전·counts 불일치 및 중복/고아 상태를 조회한다.
- **C2**: 경로/자격증명/원문을 노출하지 않는 logs/metrics와 제한된 권한의 점검 명령을 제공한다.
- **C3**: 실제 고장 주입으로 이상 탐지·dry-run 복구 안내·운영 runbook의 일치를 검증한다.

### #20: 새 API의 최소 권한·경로·필터 보안 회귀

- **C1**: 새 SQL/worker/collection API에 reader/writer/admin 권한을 고정하고 PUBLIC EXECUTE 회수와 선택적 grants를 검증한다.
- **C2**: 경로·symlink·필터 injection·oversized input·작업 취소를 검사하고 신뢰 OS 운영자/공유 corpus 지원 경계를 명시한다.
- **C3**: 현재 보안 감사·민감정보 검사 및 지원 범위 내 실제 권한 회귀를 통과한다. 다중 tenant 격리나 분산 ACID를 증명 없이 주장하지 않는다.

### #21: 1.0 SQL/CLI 계약·설치·검색 예제 고정

- **C1**: 함수/CLI 옵션·오류·NULL/차원/finite vector·순서·취소·일관성 계약과 SemVer 정책을 고정한다.
- **C2**: 깨끗한 PG16 환경에서 Docker/설치 패키지·실제 embedding·검색·업데이트·삭제·복구 예제를 따라 실행한다.
- **C3**: ROADMAP/BLUEPRINT/README/지원표의 오래된 완료 표시를 실제 release gate와 맞추고 미지원 기능을 명시한다.

### #22: 1.0 RC 통합 검증과 최종 출시 판정

- **C1**: 동일 commit/lock/artifact로 설치·업그레이드·정합성·복구·품질·SLA·권한·고지/SBOM gate를 모두 검증한다.
- **C2**: 재현 명령·checksum·CI·기능/운영 제한을 묶은 검토 가능한 RC 보고서와 배포 후보를 준비한다.
- **C3**: 사용자의 별도 최종 출시 승인 전에는 이 이슈를 완료로 닫거나 정식 1.0 tag/binary release/운영 배포를 수행하지 않는다.

The final release decision requires explicit user approval; the batch prepares the review report and waits.
